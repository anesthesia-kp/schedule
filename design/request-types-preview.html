Request types DESIGN PREVIEW — NOT THE APP
A mockup. No database, no real data, nothing here writes anything. It exists so the shape can be argued with before it becomes code — the same way the shift editor and the Reports section were done.
The 27 entries below are the owner’s own list, transcribed from screenshots of the current system and confirmed by him as complete. They are the one thing on this page that is not invented.
⚠️ EVERYTHING ELSE IS INVENTED — the people, the dates, the shift lists behind each entry, the queue. None of it is real data. Which shifts actually belong in “Oakland call” or “Late shifts” is for the owner to set; here they are filled with plausible nonsense so the screen has something to draw.

Reached from the Requests page — a ⚙ Request types → button at the top of the queue, exactly where the owner asked for it. It is its own page rather than a panel inside Requests because ruling §20 gives each page one master lock, and it puts Requests among the daily-work pages that open unlocked. Configuration must open locked. Both cannot be true on one page without a second per-section lock, which §20 rejects.

Shift lists — what the “work” and “avoid” entries point at
Only some shifts can be requested at all — owner, 16 Aug: “Not all shifts can be requested, that’s why i want just these.” So these lists are set by an admin, never worked out by the app. Same control and same rule as the Overnight-call tag, which shipped in build 51.

A list of one shift is still a list — that is what lets PACU MD and Req OAK Call use one mechanism instead of two.
A list can legitimately be empty, and that has to be visible. The Oakland / Richmond and AM / PM entries cannot be filled in until stage 1 sets sites and times on shifts — and times are currently blank everywhere by ruling §38. An entry pointing at an empty list must say so, on both the admin page and the staff picker, rather than quietly matching nothing. That is the failure mode this design is most worried about.

Defect 1 is still open and this makes it bigger. Approving from a queue writes the assignment with no eligibility, capacity, vacation or collision check — the hand-editing path checks, this path does not. Going from 4 request types to 27 multiplies the ways into that gap. Stage 6 closes it. Until then a work approval should carry a warning at the point of the click, which is what the amber note on each row stands in for.
