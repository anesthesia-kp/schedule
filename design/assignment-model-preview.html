It clears both slots and sets one. If he already held a day shift it is gone — no warning, no record, and nothing in the audit log naming what was taken away. Three operations, and none of them is “replace”. addShift appends and never removes. removeShift removes the shift you named and nothing else. setOff touches the flag and no shifts. Replacing is remove-then-add, said out loud in one confirmation, rather than an implicit consequence of a dropdown changing value (§3, §8).
Nothing is ever blocked (§4). Try adding Call 24 and then Call 16 — they overlap, so it warns and lets you do it, and records the override with who, when and which rule. Try RCH-ICU A alongside an Oakland shift: §18 makes site a property of the whole day, so that is not a timing question and no gap fixes it — the warning says so in different words.

There is no migration
No mass rewrite, no one-shot self-marking migration, and no moment where the app is half converted. Defect 24 is the standing warning — the v2 catalog seeding marked itself done, so editing the source constants afterwards has no effect on a database that was already seeded. That pattern is not repeated here.

Instead: one normaliser, used by every reader. Old months keep working for ever, unread and unrewritten. A cell converts the first time somebody actually changes it, in the same write that changes it.
shiftsOf(cell): if cell.a exists → that is the truth otherwise → build it from [cell.day, cell.call], skipping blanks
One rule, absolute: if a is present, day and call are ignored — never merged, never a fallback. Two sources for one answer is how the eligibility grid nearly went wrong (§19).
