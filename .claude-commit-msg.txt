Build 52 / 27 — THE ASSIGNMENT MODEL: a list per person per day. Closes defect 2.

Stage 3. Both pages. No firestore.rules change, so NO Firebase console step.

THE RULING THIS SATISFIES

  DECISIONS §8, the owner, 15 Aug:
    "People can definitely have 2 daytime shifts. No shift can ever just be replaced.
     Good to have the warning, but some day shifts are compatible together."

WHAT WAS WRONG

  A cell was {day, call, off} — two slots and a flag. That is not a storage detail; it is
  a rule about the world, and it was the wrong rule. A person could hold at most one day
  shift, because the second one deleted the first.

  Defect 2 in the actual code. Approving a shift request did this:

      patch = { ...cur, day:null, call:null, off:false, [kind]: r.shiftId }

  It cleared BOTH slots and set one. If the person already held a day shift it was gone —
  no warning, no confirmation, and NOTHING IN THE AUDIT LOG naming what was taken away.
  They were told their call request was approved; they were not told they had been taken
  off their day shift, and nobody was covering it. The same shape appeared in the swap
  apply and in auto-populate.

THE NEW SHAPE

  days[DD][user] = { a:[{s, by, at, via}], off }

  `a` IS THE TRUTH WHENEVER PRESENT. The legacy day/call pair is read only for cells
  written before this build and is NEVER merged with `a` — two sources for one answer is
  what §19 warns about, and it is how the eligibility grid nearly went wrong.

  `via` is one of manual · auto · request · swap · open · legacy. It answers the question
  people actually ask — "who put me on that?" — and it is what the per-person change feed
  (§6, stage 7) will be built from.

THERE IS NO MIGRATION

  No mass rewrite, no one-shot self-marking migration, and no moment where the app is half
  converted. Defect 24 is the standing warning: the v2 catalog seeding marked itself done,
  so editing the source constants afterwards has no effect on an already-seeded database.
  That pattern is not repeated.

  Instead: ONE NORMALISER, used by every reader. Old months keep working for ever,
  unread and unrewritten. A cell converts the first time somebody actually changes it, in
  the same write that changes it, dropping day/call at that moment.

  Roughly twenty read sites were routed through it: the grid, both Stats modes,
  windowShiftCounts, both auto-populate paths, the capacity check, request and swap
  approval, dashCoverage, the Reports collector from build 51, and the staff page's
  personal calendar and Quick View.

THREE WRITERS, AND NONE OF THEM IS "REPLACE"

  addCellShift  — appends. Never removes anything.
  removeCellShift — removes the shift you named, and nothing else.
  setCellOff    — sets the flag. Touches no shifts.

  All three run inside a transaction against the FRESH cell, so two admins editing the same
  day can no longer lose each other's change — the old whole-cell mergeFields write had
  exactly that hole. Replacing is now remove-then-add, said out loud in one confirmation
  (§3), rather than an implicit consequence of a dropdown changing value.

THE DAY CELL

  Two dropdowns became a list with an Add button. Each held shift shows where it came from
  and has its own named Remove. Adding confirms and promises in words that nothing already
  there will be removed. Marking someone off warns that it does NOT clear their shifts.
  Every action applies on its own and is audited by name, so there is no batch of unsaved
  edits for an incoming snapshot to destroy (cf. defect 12).

REQUEST APPROVAL, REWRITTEN

  · shift / claim — ADDS. Removes nothing. The off flag is cleared (leaving someone both
    off and assigned helps nobody) and the audit entry says that it was.
  · dayoff — removes their shifts, because that is what the request MEANS, but names every
    one of them in the audit log. That naming is precisely what defect 2 never did.
  · nocall — now points at the OVERNIGHT-CALL TAG (§27), the list the admin set, instead of
    "whatever sat in the call slot". Same correction §25 made everywhere else. Eye Call is
    the reason: it is in the call family, runs 07:30-15:30, and SURVIVES a no-call request.

SWAPS

  A leg now moves the actual shifts the giver holds of the named kind — add to the
  receiver, then remove from the giver, two named operations. The old version copied a slot
  wholesale, which overwrote whatever the receiver already had in it. Whatever either side
  holds of the OTHER kind is now left alone.

AUTO-POPULATE — POLICY DELIBERATELY UNCHANGED

  One shift of each kind per person per day, exactly as before. This build changes how
  assignments are STORED, not who gets what; mixing a data-model change with a
  scheduling-policy change would make any regression impossible to attribute. Whether
  auto-populate should stack shifts is a rules question and belongs to stage 5.

CARDINAL RULE — no schedule work may degrade the live Vacation Auction

  · sched/isolation-test.mjs — 27/27. Zero new write paths to any vacations/* document.
  · FTE independence — 5/5.
  · AUCTION battery, on the owner's machine — 14 suites, 1074 assertions, green.

  WORTH RECORDING: the auction battery went RED before it was fixed, for the second time
  on a schedule-only change. test-audit-fixes.mjs is an auction suite that reads the
  SCHEDULE admin page and pins the order of operations in decideReq — the open-shift claim
  transaction must run BEFORE anything reaches the schedule, and a lost race must return
  before any write. That property is still true; the suite anchored it on the literal
  string "if(patch) await mergeFields", which this build replaced with mutateCell(). The
  ANCHOR was updated. The assertion was not weakened. Nothing in production was affected —
  but it is the second live example of the two sites touching, and it is why the auction
  battery runs after every schedule change and not only the ones that look shared.

WHAT THIS DOES NOT FIX

  · Defect 1 stays open — request and swap approval still write assignments without
    checking eligibility, capacity, vacation or collision. Stage 3 makes the WRITE safe
    (nothing is silently destroyed); it does not make the DECISION checked. Stage 6 is what
    closes that, and this build is a prerequisite for it, not a substitute.
  · Defect 3 stays open — swap apply is still not atomic with swap status.
  · Defect 8 gets closer to mattering — a list with provenance is bigger than two strings,
    and each month is still one document against a 1 MB cap.

about.
